## Functional Requirements (FR)

| ID      | Type        | Description                                                                                             | Priority | Acceptance Criteria                                                                                                                                                                      | Rationale                                                                        |
| :------ | :---------- | :------------------------------------------------------------------------------------------------------ | :------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------- |
| **FR-001** | Functional  | The system shall generate weekly meal plans strictly adhering to user macro-nutrient constraints and allergen exclusion lists. | High     | **Pass:** A test profile with a peanut allergy and a <1500 kcal/day goal is created. The generated 7-day menu contains zero peanut ingredients and the daily average calorie count is <= 1500. <br/> **Fail:** The generated menu contains peanuts or exceeds the calorie goal. | This is the core function of the personalization engine.                         |
| **FR-002** | Functional  | The system shall allow a Subscriber to create and update their personal metabolic profile (allergies, diabetic limits, calorie goals). | High     | **Pass:** A logged-in Subscriber can navigate to their profile, add "Dairy" to their allergen list, and save the changes. The new allergen is reflected in the next meal plan generation. <br/> **Fail:** The Subscriber cannot save profile changes, or the changes do not persist. | Personalization is impossible without accurate and up-to-date user input.      |
| **FR-003** | Functional  | The system shall allow a Dietitian to review, override, and approve a meal plan generated for a subscriber. | Medium   | **Pass:** A Dietitian can log in, select a subscriber's auto-generated plan, replace one meal with another from a predefined list, and click "Approve". The subscriber's view of the plan is updated. <br/> **Fail:** The Dietitian cannot modify or approve the plan. | Provides essential clinical oversight and quality control, a key feature for a "clinical" service. |
| **FR-004** | Functional  | The system shall process recurring weekly payments for active subscriptions using a stored payment method. | High     | **Pass:** On the subscription renewal date, the system successfully charges the subscriber's registered credit card via a payment gateway API and extends the subscription end date by 7 days. <br/> **Fail:** The system fails to trigger the payment or handle a failed payment notification. | The service is a subscription model; automated billing is critical for business viability. |
| **FR-005** | Functional  | The system shall track and display the daily delivery fulfillment status (e.g., "Preparing", "Out for Delivery", "Delivered"). | Medium   | **Pass:** After a daily meal is dispatched, a Subscriber can log in and view a status of "Out for Delivery" for that day's meal. The status updates to "Delivered" upon confirmation. <br/> **Fail:** The status is not available or is not updated in a timely manner. | Fulfills the "tracks daily delivery fulfillment" part of the problem statement and manages user expectations. |

## Non-Functional Requirements (NFR)

| ID      | Type                   | Description                                                                                                                        | Priority | Acceptance Criteria                                                                                                                                                                                                                                   | Rationale                                                                                                         |
| :------ | :--------------------- | :--------------------------------------------------------------------------------------------------------------------------------- | :------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------ |
| **NFR-001** | Performance & Security | The subscription engine must support schedule modifications (pause, skip, reschedule) up to 12 hours before dispatch.           | High     | **Pass:** A load test simulating 500 concurrent users attempting to pause their subscription 12 hours and 1 minute before dispatch succeeds with an average response time of <2 seconds. The same test run 11 hours and 59 minutes before dispatch fails for all users. <br/> **Fail:** The system allows modifications within the 12-hour window, or it crashes under load. | This sets a critical business rule for logistics and food preparation, preventing waste and ensuring fulfillment. |
| **NFR-002** | Security & Compliance  | All subscriber data, especially Protected Health Information (PHI) like allergies and medical constraints, must be encrypted at rest and in transit. | High     | **Pass:** A third-party security audit confirms that all database fields containing PHI are encrypted using AES-256. Network traffic analysis confirms all communication between the client and server is over TLS 1.3. <br/> **Fail:** Any PHI is stored in plain text or transmitted over an unencrypted channel. | Essential for meeting legal and ethical standards (like HIPAA in the US) for handling sensitive patient health data. |
